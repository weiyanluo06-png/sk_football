## 0. 十分钟接手指南

如果只来得及读一节，请先记住以下规则。

1. 网站是一个**记录和纪念学院足球队**的静态网站，不是学院通知、公示或商业宣传网站。
2. 球员基础资料、比赛数据、评分原值、赛事索引和赛程的主数据源是 `data/生康足球队数据源.xlsx`。
3. 修改 Excel 后，运行 `python tools/sync_team_workbook.py`，脚本会更新 `js/team-data.js` 中的球员、赛事和比赛数据。
4. 球员照片、个人介绍、队友评价、固定首发、队史节点不完全由 Excel 管理，仍需检查 `js/team-data.js`。
5. 首页轮播和招新内容在 `index.html`；影像墙文字和照片路径在 `js/gallery-data.js`。
6. 主色只能围绕深绿、草绿、纸白、墨黑展开。不要加入紫色渐变、霓虹色、装饰光球或通用 SaaS 风格。
7. 所有文案必须来自真实队史、真实比赛或队员信息。禁止用空泛 AI 文案补齐资料。
8. 球员和比赛照片优先使用真实原图，同时准备 WebP。任何新图必须检查手机裁切和加载速度。
9. 桌面端与手机端都必须验收，尤其是首页轮播、沉浸式阵容、弹窗、影像墙和菜单。
10. 发布前运行：

```powershell
python tests\team-workbook-sync.test.py
node tests\team-memorial-refresh.test.mjs
```

11. 测试通过后再提交并推送 `main`。GitHub Actions 会自动更新 Pages。
12. 不要对远程仓库强制推送，也不要覆盖不属于本次任务的本地修改。

## 1. 项目是什么

### 1.1 项目定位

生康足球队纪念站是武汉纺织大学生物医学工程与健康学院足球队的线上档案。它记录：

- 队伍怎样在 2025 年从人数不足开始组建；
- 训练、比赛、合照、毕业与场外生活；
- 球员资料、真实数据、踢球风格和队友评价；
- 每个赛季的赛事索引和比赛记录；
- 材料学院对球队成立和成长的帮助；
- 新学期招新信息。

这个项目最重要的价值不是“信息发布效率”，而是让队员多年后仍能看到真实的人、比赛和故事。

### 1.2 产品理念

维护者应始终遵守以下理念：

- **记录优先于宣传。** 页面要像球队档案、比赛日刊物和队史相册，而不是学院公告栏。
- **真实优先于完整。** 没有资料就标明“待补充”或暂不展示，不编造进球、评价、奖项和故事。
- **人物优先于装饰。** 照片中的人不能被标题、按钮、渐变或信息卡挡住。
- **球队共同体优先于个人包装。** 可以突出球员，但整体气质仍应是同一支队伍。
- **手机体验与电脑体验同等重要。** 队员最可能从手机链接进入，不能只做大屏效果。
- **纪念感来自真实细节。** 日期、比分、球衣号码、场地、雨天、围圈、毕业照都比空泛口号更有价值。
- **修改应当可持续。** 新赛季到来后，维护者应优先更新表格和数据文件，而不是在 HTML 里重复写死同一份信息。

### 1.3 已确认的真实背景

- 建队年份：`2025`
- 球队：生康足球队
- 学院：武汉纺织大学生物医学工程与健康学院
- 常用主场：阳光校区足球场
- 材料学院是球队长期认可的兄弟学院
- 学校学院足球赛事通常按以下节奏进行：
  1. 上学期：十一人制纺大杯
  2. 上学期：八人制新生杯
  3. 下学期：八人制纺大杯
- 赛事档案默认优先展示：`2025 · 十一人制纺大杯`
- 招新 QQ 群：`913800697`

## 4. Excel 数据源维护

### 4.1 工作簿

主工作簿：

```text
data/生康足球队数据源.xlsx
```

当前工作表：

- `统计汇总`
- `球员数据`
- `赛事索引`
- `赛程`

### 4.2 球员数据字段

`球员数据` 当前包含：

| 字段 | 规则 |
|---|---|
| 序号 | 球员唯一数字 ID；不得与其他球员重复 |
| 姓名 | 与 `team-data.js` 的现有姓名匹配；同步保留手工资料时依赖姓名 |
| 绰号 | 档案弹窗中的球员标签 |
| 号码 | 数字；允许 0 |
| 主位置 | 只使用 `FW`、`MF`、`DF`、`GK` |
| 可胜任位置 | 使用斜杠分隔，如 `LWF/CF`、`CB/CM/GK` |
| 出场 | 非负整数 |
| 进球 | 非负整数 |
| 助攻 | 非负整数 |
| MVP | 非负整数 |
| 零封 | 只有真实有零封的队员填写；网页只在大于 0 时显示 |
| 低失球场 | 该球员出场且球队失球不超过 1 球的场次 |
| 评分 | 公式列，不手工覆盖 |
| 踢球风格 | 一个简洁且真实的风格标签 |
| 代表数据 | 公式列，不手工覆盖 |

已删除“扑救”字段，网站卡片和 Excel 都不再维护扑救次数。

### 4.3 评分规则

Excel 和同步脚本使用同一思想：

```text
基础分 6
+ 出场 × 0.08
+ 进球 × 0.35
+ 助攻 × 0.25
+ MVP × 0.25
+ 零封 × 0.15
```

如果主位置为 `DF`，额外增加：

```text
+ 出场 × 0.06
+ 零封 × 0.35
+ 低失球场 × 0.15
```

最终限制在 `6.0` 至 `9.5`，保留一位小数。

**重要：网页展示分与表格原值不同。** `main.js` 中的 `getDisplayRating()` 会让原评分低于 8 分的球员在网页端临时增加 1 分，但不会修改 Excel，也不会修改 `team-data.js` 中的原始评分。这样做是为了避免防守球员在公开档案中因数据难统计而显得过低。

未来如确定新的评分体系，应同时修改：

- `tools/sync_team_workbook.py` 的 `rating_formula()`
- `tools/sync_team_workbook.py` 的 `calculate_rating()`
- Excel 现有公式
- `tests/team-workbook-sync.test.py`
- 是否继续保留 `main.js` 的展示加分

### 4.4 同步步骤

#### 情况 A：直接修改仓库内工作簿

```powershell
cd C:\Users\A\Desktop\website
python tools\sync_team_workbook.py
```

#### 情况 B：用户给了另一个 Excel 文件

```powershell
python tools\sync_team_workbook.py `
  --source "C:\用户提供的文件.xlsx" `
  --target "data\生康足球队数据源.xlsx"
```

脚本将：

1. 必要时复制用户提供的工作簿；
2. 删除旧“扑救”列；
3. 确保存在“低失球场”列；
4. 重写评分和代表数据公式；
5. 格式化 Excel 表格；
6. 读取球员、赛事和赛程；
7. 更新 `js/team-data.js`。

### 4.5 同步后的必查项

```powershell
git diff -- data\生康足球队数据源.xlsx js\team-data.js
python tests\team-workbook-sync.test.py
node tests\team-memorial-refresh.test.mjs
```

然后人工检查：

- 球员人数是否正确；
- 号码和位置是否变化；
- 出场、进球、助攻、MVP 是否与表格一致；
- 只有零封大于 0 的球员才显示零封；
- 代表数据是否合理；
- 赛事数量与赛程数量是否正确；
- 默认赛事是否仍为期望赛事；
- 现有照片、评价和个人介绍是否仍存在。

### 4.6 同步脚本的重要风险

同步时，脚本通过**姓名**查找现有球员，再保留照片、评价和介绍。

因此：

- 不要随意改姓名中的字、空格或繁简体；
- 如果是纠正姓名，先记录该球员现有 `photo`、`bio`、`reviews`；
- 改名后检查是否被当成新球员；
- 新球员会自动得到空照片、空评价和“待补充球员介绍”，必须继续手工完善；
- 删除 Excel 中一行会导致同步后的网页球员列表也删除该球员。

### 4.7 新生展示

`新生展示` 工作表用于展示新加入球队、尚未进入正式大名单的队员。运行 `python tools/sync_team_workbook.py` 后，工作表会生成 `js/newcomer-data.js` 中的 `window.NEWCOMER_DATA`；这是新生展示数据的唯一网页输出文件，不要手动把新人写入 `js/team-data.js` 的 `players` 数组。

工作表共 12 个字段：

| 字段 | 填写规则 |
|---|---|
| 排序 | 必填；数字越小越靠前 |
| 姓名 | 必填；填写真实姓名 |
| 年级 | 必填；例如 `2026级` |
| 号码 | 未分配时留空 |
| 主位置 | 必填；例如 `CM`、`CB` |
| 可胜任位置 | 可选；多个位置用 `/` 分隔 |
| 惯用脚 | 可选；填写左脚、右脚或双足 |
| 踢球风格 | 可选；只写真实、简短的训练观察 |
| 自我介绍 | 可选；一句真实介绍，建议不超过 30 个汉字 |
| 照片文件名 | 可选；仅填写 `assets/players/` 中的文件名，例如 `lin-mou.webp` |
| 照片焦点 | 可选；使用 `50% 30%` 这类 `object-position` 值调整裁切焦点 |
| 展示状态 | 必填；只有精确填写 `展示` 才会输出，`隐藏`或其他值均不展示 |

新增或更新新人时，先将真实照片放入 `assets/players/`，推荐 WebP、竖版构图、人物清晰可辨；不得用网络人物图或 AI 人像替代。同步后需在桌面端和手机端检查照片裁切、横向卡片滚动和“新生”导航锚点。

当没有任何“展示”记录，或 `js/newcomer-data.js` 加载失败时，新生板块仍保留，显示三张静止的“新生资料待更新”占位卡。不得为占位状态编造姓名、位置、照片或评价。

新生进入正式大名单时：

1. 在 Excel `球员数据` 新增该球员并填写正式资料；
2. 从 `新生展示` 删除该行，或将“展示状态”改为 `隐藏`；
3. 运行同步脚本；
4. 在 `js/team-data.js` 为正式球员补充照片、个人介绍和队友评价；
5. 视真实情况决定是否加入 `startingLineup`，并确认新生板块不再出现该球员、正式球员档案已经出现该球员。

新生数据与正式球员数据隔离：同步脚本只把“展示”记录写入 `js/newcomer-data.js`，不会修改 `window.PONYTAIL_DATA.players`、正式球员人数、`startingLineup`、战术板候选池、球员弹窗或现役统计。新人不记录出场、进球、助攻、MVP、零封或评分；这些数据只在其进入“球员数据”后按正式维护流程统计。

## 5. 添加或更新球员

### 5.1 只更新数据

适用于出场、进球、助攻、MVP、零封、低失球场变化。

1. 修改 Excel 的 `球员数据`。
2. 不要修改评分和代表数据公式列。
3. 运行同步脚本。
4. 运行两组测试。
5. 打开球员弹窗核对。

### 5.2 添加新球员

1. 在 Excel `球员数据` 末尾新增一行。
2. 分配一个从未使用过的 `序号`。
3. 填写姓名、号码、主位置、可胜任位置和真实数据。
4. 填写踢球风格。
5. 运行同步脚本。
6. 把照片放入 `assets/players/`。
7. 在 `js/team-data.js` 对应球员对象补充：

```js
avatarIcon: 'fa-futbol',
reviews: ['队友对他的真实评价'],
bio: '基于球队表格或队友提供的真实介绍。',
photo: 'assets/players/new-player.webp'
```

8. 如果球员进入首发，修改 `startingLineup`。
9. 将 `index.html` 首页“球员档案”数量从旧数字更新为新数字。
10. 检查随机三人展示和全队档案。

### 5.3 球员照片规范

- 文件夹：`assets/players/`
- 文件名：小写拼音或稳定英文 slug，例如 `wuyuze.webp`
- 推荐构图：竖版、脸部清晰、主体居中或略偏上
- 最小建议：`800 × 1000`
- 推荐同时保留：
  - 原始 JPG/PNG
  - 网页 WebP
- 不要拉伸照片；
- 不要用陌生网络人物替代真实队员；
- 不要使用会造成身份误认的 AI 人像；
- 人脸在阵容小卡中应仍可辨认；
- 背景复杂时，优先通过裁切改善，不叠加过多文字。

startingLineup: {

## 8. 视觉与审美规范

### 8.1 核心气质

关键词：

- 校园足球
- 队史档案
- 比赛日刊物
- 真实、克制、有温度

不应呈现为：

- 夸张电竞网站；
- 全屏渐变营销页；
- 只有装饰、没有真实人物的“高级感”页面。

### 8.2 配色

CSS 变量是唯一配色入口：

```css
--green: #1f7a4d;
--green-dark: #0f3d2a;
--line: #d7eadf;
--cream: #f7f4ed;
--paper: #fffdf8;
--ink: #17231d;
--muted: #65746b;
--gold: #d8a63a;
--blue: #315f8f;
--red: #bb4b4b;
```

使用规则：

- 深绿：品牌、重点信息、阵容信息卡；
- 草绿：按钮、标签、激活状态；
- 纸白和米白：页面底色和档案感；
- 墨黑：正文和标题；
- 金色：少量荣誉、焦点和键盘焦点环；
- 蓝色：平局；
- 红色：负场和必要警示；
- 不新增大面积紫色、蓝紫渐变、咖啡棕或霓虹色。

### 8.3 字体

- 中文正文：`Noto Sans SC`
- 中文叙事标题：可使用 `Noto Serif SC`
- 数字、英文标签：`Oswald`
- 系统回退：`Microsoft YaHei`, Arial

规则：

- 大标题只用于真正的页面主标题或沉浸式阵线名称；
- 小卡片标题不要使用英雄页字号；
- 中文正文保持正常字距；
- 英文 kicker 可适当增加字距；
- 不用多种花体混搭；
- 不让字压住人脸或超出卡片。

### 8.4 圆角、阴影和边框

```css
--radius-sm: 8px;
--radius-md: 12px;
--radius-lg: 18px;
--radius-full: 999px;
--shadow: 0 18px 45px rgba(17, 35, 27, 0.16);
```

规则：

- 普通卡片优先 `8px`；
- 模态框和大型展示区可用 `12-18px`；
- 胶囊圆角只用于标签、筛选按钮和状态；
- 不把所有板块做成悬浮卡片；
- 不在卡片里再套卡片；
- 阴影只用于层级，不用于发光装饰。

### 8.5 页面布局

- 页面板块使用全宽区段，内容居中；
- 标准区段使用 `.section`；
- 每个板块保持明显上下节奏；
- 运营工具类区域可以更密，故事和照片区域应更有呼吸感；
- 固定比例元素必须设置稳定尺寸或 `aspect-ratio`；
- 不靠字体或内容把容器“撑到刚好”；
- 手机端优先单列，不强行缩小桌面多列。

### 8.6 动效

现有动效：

- 区段滚动出现；
- 首页图片淡入和轻微缩放；
- 沉浸式阵线聚焦；
- 影像墙轻微抬升；
- 点赞心形粒子；
- 队友评价弹幕。

规范：

- 常规交互约 `0.25s`；
- 区段出现约 `0.7s`；
- 动效必须平滑，不造成页面跳动；
- 滚动监听使用 `requestAnimationFrame` 或观察器；
- 手机纵向滚动不能被横向滑动组件锁死；
- 必须支持 `prefers-reduced-motion`；
- 不加无意义的持续旋转、漂浮光球或背景粒子。

## 9. 组件级规范

### 9.1 首页

- 首屏必须首先看到球队或真实比赛；
- 标题放在照片空白区；

- 一级索引是年份，二级索引是杯赛；

- 球场保持足球场比例；

- 右侧绿色信息卡显示当前阵线和当前球员；
- 非聚焦球员仍然可以点击打开档案；
- 不允许透明覆盖层挡住球员点击。

手机端：

- 正常上下滑离开该板块；
- 左右滑球场或绿色信息卡切换阵线；
- 阵线循环切换；
- 底部标签明确告诉用户可以切换；
- 后卫四人必须始终排在同一行；
- 门将不能被绿色信息卡挡住。

### 9.4 球员档案

- 卡片显示真实姓名、号码、位置、风格；
- 弹窗显示出场、进球、助攻、MVP、评分；
- 只有零封大于 0 时显示零封；
- 不显示扑救次数；
- 队友评价用弹幕表现；
- 没有评价时不要显示空白评价框；
- 评分展示规则与原始数据区分清楚。

### 9.5 影像墙

- 分类来自现有照片内容；
- 瀑布流高度可有变化；
- 点击照片打开详情；
- 点击点赞不能同时打开照片；
- 图片进入视口附近再加载；
- 每张照片必须有标题、类别和真实说明。

### 9.6 新增板块

新增前先回答：

1. 这个板块是否服务“记录、纪念、队员体验”？
2. 数据来自哪里？
3. 手机端最主要的动作是什么？
4. 是否能复用现有 section、标题、按钮和配色？
5. 是否会影响首屏加载？
6. 没有真实内容时是否应该延后上线？

实现时：

- 使用现有 CSS 变量；
- 使用 `.section__kicker`、`.section__title`、`.section__subtitle`；
- 使用 Font Awesome 现有图标；
- 保持键盘焦点样式；
- 不新增独立设计系统；
- 不加入与纪念站无关的营销段落。

## 10. 前端工程规范

### 10.1 技术栈

- HTML
- CSS
- 原生 JavaScript
- Font Awesome
- Google Fonts
- GitHub Pages

当前没有框架、构建器和数据库。除非需求明显扩大，不要为了一个小功能引入 React、Vue、打包器或复杂状态管理。

### 10.2 JavaScript 约定

- 数据放在 `window.PONYTAIL_DATA` 和 `window.PONYTAIL_GALLERY`；
- 渲染逻辑放在 `main.js`；
- 所有用户文本写入 HTML 前使用 `escapeHtml()`；
- DOM 元素通过现有 `$()` 辅助函数获取；
- 滚动事件必须节流或使用 `requestAnimationFrame`；
- 图片懒加载优先使用 `IntersectionObserver`；
- 弹窗打开后把焦点移到关闭按钮；
- 弹窗关闭后焦点回到触发元素；
- Escape 可关闭弹窗；
- 手机横向手势必须判断横向位移大于纵向位移。

### 10.3 性能规则

- 首页首图立即加载；
- 下一张首页图延迟预加载；
- 影像墙延迟加载；
- 球员照片使用 WebP；
- 手机首页使用独立小图；
- 避免在滚动事件中频繁查询和重排整个页面；
- 新增大图前先压缩；
- 不把视频、原始大图或 Excel 放进首屏加载链路。

### 10.4 可访问性

- 图片必须有 `alt`；
- 图标按钮必须有 `aria-label`；
- 菜单维护 `aria-expanded`；
- 标签切换维护 `aria-selected`；
- 弹窗使用 `role="dialog"` 和 `aria-modal="true"`；
- 键盘焦点必须清晰；
- 颜色之外还需有文字；
- 动画遵守减少动态偏好。

## 14. 已知的维护陷阱

1. **评分有两层。** Excel/JS 是原始分，网页对低于 8 分的球员临时加 1。
2. **Excel 不是全部资料。** 照片、介绍、评价、首发和队史仍要手工维护。
3. **球员匹配依赖姓名。** 改名后可能失去现有照片和评价关联。
4. **首页球员人数是写死的。** 新增或删除球员后同步修改 `index.html`。
5. **默认赛事不会由表格自动决定。** 新赛事上线后检查 `defaultCompetitionId`。
6. **阵容编辑不持久。** 页面点选换人不会保存到代码。
7. **点赞不持久。** 当前只是本地视觉特效。
8. **二维码不能由 AI 重绘。** 必须使用原始二维码文件。
9. **手机与桌面使用不同首页图片。** 只换桌面图会造成手机仍显示旧图。
10. **缓存可能让修改看起来没生效。** 使用新文件名或更新资源版本参数，再强制刷新。
11. **比赛筛选依赖赛事名称和日期年份。** 名称必须与赛事索引完全一致。
12. **新球员不会自动拥有真实介绍。** 同步后必须人工补充。

## 17. 维护原则总结

下一位维护者可以改变布局、增加板块、优化性能，但不能改变这个网站的核心：

> 它首先是一支学院足球队的真实记忆，其次才是一个前端作品。

每次更新前应问：

- 这段内容是真的吗？
- 队员多年后看到会觉得这是他们的球队吗？
- 照片中的人是否被尊重？
- 手机访问是否顺畅？
- 下一位维护者是否还能继续更新？

只要这五个答案都是肯定的，项目就仍然走在正确方向上。
